# خطة إصلاح وإكمال الوكيل عن مستحق محدد

تاريخ الفحص: 2026-10-15.
آخر تدقيق للمراجع: 2026-10-16.
الحالة: اكتمل فحص الشيفرة وإعداد خطة التنفيذ. لم يبدأ تعديل كود الميزة أو قاعدة البيانات.

## 1. الهدف والقرارات

إتاحة تسجيل وكلاء لمستحقين مختلفين داخل الملف نفسه، وتحصيل كل وكيل حصة المستحق الذي يمثله، مع سلامة التعديل والإيقاف والمراجعة والصرف والاستيراد.

### قرارات مثبتة

- يبقى الربط المباشر `Agent.EntitledID` اختيارياً؛ `null` يعني وكيلاً عاماً للملف.
- وكيل نشط واحد لكل نطاق، مع السماح بوكلاء لمستحقين مختلفين داخل الملف.
- يبقى مستلم الوكيل مرتبطاً بواسطة `SalaryRecipient.AgentID` فقط. يستنتج نطاق المستحق من الوكيل؛ لا يلزم تعديل قيد `CK_SalaryRecipient_TypeOrGuardianWithEntitled`.
- يُمنع اجتماع وصاية نشطة ووكالة نشطة للمستحق نفسه في أي ترتيب للتعيين.
- فقد أهلية المستحق يوقف وكيله ومستلمي حصته، ولا يعيدهم تلقائياً بمجرد استعادة الأهلية.
- إنشاء الوكالة وتجهيز مستلم المعاش عمليتان منفصلتان، كما في المسار الحالي.
- **قرار المستخدم في هذه المراجعة: منع صرف الملف كله حتى تعيين جميع المستلمين.** لا يُصرف جزء من الملف ولا يعاد توزيع حصة غير ممثلة على بقية المستلمين.

المصدر السابق: [تصور الميزة](feature-context-agent-entitled-person-link.md)، خصوصاً القرارات المحسومة وقرار إبقاء `AgentID` فقط في مستلم الوكيل. بعض وصفه وأرقام أسطره تعود لما قبل التنفيذ الجزئي وإعادة تنظيم الخدمات؛ المرجع للتنفيذ هو الكود الحالي.

### حدود التغيير

تقتصر المعالجة على الوكالة والمستحق والوصاية ومسارات الصرف المتصلة بها. لا تعاد هيكلة الخدمات الأخرى، ولا تنشأ علاقة متعددة الأطراف أو سجلات أشخاص موحدة بين الملفات. يبقى دفتر الصرف على مستوى الملف؛ تحويله إلى دفتر لكل مستحق يحتاج طلباً مستقلاً.

## 4. التصميم المستهدف

### 4.1 نطاق الاستحقاق

قاعدة واحدة تستخدم في استبدال المستلم وفحص التعارض والإيقاف والتقارير:

| نوع المستلم | نطاق الاستحقاق |
|---|---|
| مستحق مباشر | `SalaryRecipient.EntitledID` |
| وصي عن مستحق | `SalaryRecipient.EntitledID` مع التحقق من علاقة الوصاية |
| وكيل عن مستحق | `SalaryRecipient.Agent.EntitledID` |
| متقاعد أو وكيل عام | نطاق عام للملف |

يوضع منطق المطابقة وإنهاء السجلات في مساعد داخلي صغير داخل Infrastructure، قابل للترجمة إلى SQL، ويستقبل المستودعات القائمة. لا ينشئ معاملات أو يحفظ التغييرات من تلقاء نفسه. تستعمله الخدمات المختلفة لتجنب تكرار المقارنة الخاطئة، دون إنشاء اعتماد دائري بين محرك الأهلية وخدمة المستلمين.

تضاف إلى DTO قراءة المستلمين حقول `EffectiveEntitledID` و`EntitledPersonName`؛ لا يعاد استخدام حقل الطلب `EntitledID` لإرسال تركيب يرفضه قيد قاعدة البيانات.

### 4.2 التعديل والتاريخ

- غياب المستحق في طلب التعديل يعني الحفاظ على الربط القائم. يضاف مؤشر صريح مثل `UpdateEntitledScope` للتمييز بين طلب تغيير النطاق وطلب تعديل البيانات الشخصية.
- فك الربط إلى وكيل عام يتطلب طلب تغيير صريح. تحديث الصورة يصبح إجراء مخصصاً وفق نمط `SalaryRecipientsController.UploadPhoto`، فلا يعيد إرسال بقية البيانات.
- إذا سبق استخدام سجل الوكيل في أي مستلم معاش، يمنع نقل السجل نفسه إلى مستحق آخر، حتى بعد إنهاء الصرف؛ تنشأ وكالة جديدة. هذا يحمي تفسير بنود الصرف السابقة لأن النطاق مستنتج من الوكالة الحالية.
- تبقى تغييرات الاسم والهوية خاضعة للتدقيق والتعارض؛ إنشاء سجل أشخاص أو لقطات مالية تاريخية جديدة خارج هذا الإصلاح.
- إنهاء الوكالة يضبط حالة النشاط والتدقيق وينهي مستلميها؛ لا يستخدم لتغيير تاريخ الانتهاء التعاقدي إلى وقت التعطيل.

### 4.3 التغطية والحصص وفق قرار المستخدم

- في وضع صرف الحصص: يستخرج جميع المستحقين المطلوب تمثيلهم، ويطابق لكل منهم مستلماً صالحاً واحداً: المستحق أو وكيله أو وصيه.
- المستلم المعلق أو المرفوض أو الوكيل المعطل/المنتهي لا يعد تغطية صالحة. لا يسقط المستحق من مجموعة التغطية لمجرد تعليق مراجعة مستلمه.
- حصة مستلم الوكيل مشتقة من حصة المستحق المعتمدة. تبديل المحصل لا يغير حصة صاحب الحساب.
- لا يولد أي بند للملف إذا نقص مستلم، أو تكرر نطاق، أو غابت حصة لازمة، أو لم يساو مجموع الحصص 100%. تظهر الأسباب وأسماء المستحقين الناقصين في نتيجة التوليد.
- مثال قبول: معاش 100,000 وحصص 50/30/20؛ وجود مستلمين للحصتين 50 و30 فقط ينتج صفر بنود للملف. عند اكتمال الثلاثة تصبح البنود 50,000 و30,000 و20,000.
- فروق التقريب تعالج بصورة حتمية في آخر بند بعد ثبوت اكتمال الحصص فقط، دون تطبيع نسب ناقصة إلى 100%.
- يبقى مسار المستلم العام للملف قائماً. يمنع خلط مستلم عام مع مستلمي حصص في صرف متزامن؛ التحويل بين الوضعين إجراء واضح ينهي الوضع السابق بعد التحقق، ولا تفسر وكالة عامة تلقائياً بأنها تمثل حصصاً محددة.
- وجود سجلات وكلاء عامة وخاصة معاً مسموح؛ القيد السابق يخص طريقة الصرف النشطة، لا تسجيل الوكالات.

### 4.4 الأهلية والمرفقات والتاريخ

يختلف تجهيز الوكالة عن أهلية تحصيل المعاش. يمكن تجهيز بيانات ومستندات مع نواقص قابلة للاستكمال، لكن الصرف يتطلب اجتياز الأهلية والمراجعة والوثائق المطلوبة. لا يعاد تفعيل وكالة ألغاها توقف المستحق تلقائياً.

يمنع الربط الجديد بمستحق متوفى أو محذوف أو من ملف آخر. تعرض حالة المستحق الموقوف وسبب إيقافه عند الاختيار؛ نواقص التجهيز لا تتحول إلى سماح بالصرف. تستخدم قواعد الأهلية القائمة دون اختراع قواعد قانونية جديدة.

تتحقق تواريخ الإصدار والانتهاء بترتيب صحيح، ويظل يوم الانتهاء صالحاً حتى نهاية اليوم وفق توقيت اليمن. الوكالة المنتهية تمنع الاختيار والتوليد حتى لو بقي علم نشاطها مخزناً؛ إنهاؤها واستبدالها يتمان بعملية صريحة.

**ملاحظة توافق:** `YemenDateTimeConverter.cs` الحالي يكتب UTC مع `Z`، وتثبت ذلك `DateTimeContractTests`، بينما نص ADR 0001 القديم يصف وقت اليمن بلا لاحقة. تستعمل الواجهة أدوات `@/lib/date` لتطبيع المدخل والعرض، وتختبر القيمتين والحد اليومي. لا تغير هذه الميزة محول التواريخ العام ولا تقتطع تاريخاً من نص UTC باستخدام `split('T')`.

## 5. مراحل التنفيذ

### P0: تثبيت خط الأساس وفحص البيانات

- حفظ حالة الملفات المستهدفة، ومخرجات lint الحالية قبل أي تعديل UI.
- إضافة فحص SQL للقراءة فقط يحدد: وجود عمود الربط ومفاتيحه وفهارسه، الوكلاء المتكررون، الوكالات لمستحق من ملف آخر، اجتماع وصي ووكيل، وتعدد مستلمين لنفس النطاق الفعلي.
- تضمين فحص المستلمين المرتبطين بوكلاء معطلين/محذوفين، الحصص الناقصة أو المتعارضة، وبنود المسودات التي تشير إليهم.
- مقارنة مخطط قاعدة البيانات مع إعداد EF؛ وجود `plan/migration_agent_entitled.sql` لا يثبت تطبيقه.

مخرج المرحلة: `scripts/agent-entitled-preflight.sql` ونتيجة فحص بيئة اختبار عند توافرها. لا تسوّى العلاقات الملتبسة أو الحوالات السابقة تلقائياً.

### P1: توحيد النطاق وحماية الوكالة

الملفات: `AgentDtos.cs` و`IAgentService.cs` و`AgentsController.cs` و`AgentService.cs` و`Validators.cs`، ومساعد النطاق الداخلي الجديد.

- تطبيق نطاق الفرع قبل البحث والقراءة والكتابة، عبر `IBranchScopeProvider` و`RetirementFile.PensionBranchID`. المستخدم غير المركزي بلا فرع لا يحصل على وصول عام.
- فحص انتماء المستحق، وتكرار النطاق، والوصاية، وصلاحية الملف للتعديل، قبل تغيير الكيان أو رفع الصورة.
- دعم التعديل الصريح للنطاق ومنع تغييره بعد استخدام الوكالة في الصرف، وإضافة مسار الصورة المنفصل.
- إرجاع `IsActive` وحالة صلاحية الوكالة ضمن قراءة البحث، بدل استنتاج النشاط من التاريخ.
- إضافة Validators متوافقة مع حدود الحقول وقواعد الهوية والهاتف في المشروع، مع تحقق أعمال مقابل داخل الخدمة.

بوابة القبول: تعديل اسم أو صورة وكيل مرتبط لا يغير المستحق؛ طلب فرع آخر مرفوض؛ تكرار نفس النطاق مرفوض بينما نطاق آخر مسموح.

### P2: الاستبدال والوصاية ودفتر الصرف

الملفات: `SalaryRecipientService.cs` و`GuardianService.cs` و`PaymentBookService.cs` وDTO قراءة المستلمين.

- استعمال النطاق الفعلي في جميع مقارنات المستلمين، والتحقق من انتماء الوكيل/المستحق/الوصي للملف ومن علاقة الوصي بالمستحق.
- اشتقاق حصة مستلم الوكيل من المستحق، وإنهاء مستلم النطاق السابق فقط، مع إبقاء بقية الحصص.
- رفض تعيين الوصي عند وجود وكيل قبل إضافة أي علاقة، والتحقق من جميع المستحقين في التعيين الجماعي قبل حفظ أي منهم.
- توجيه الإنشاء التلقائي عبر دفتر الصرف إلى منطق خدمة المستلمين نفسه، بدلاً من إنشاء سجل يتجاوز القواعد. فشل تعيين المستلم يعيد عملية إصدار الدفتر كلها إلى ما قبلها.
- منع خلط المستلم العام مع الحصص، وتوضيح التحويل الصريح بين الوضعين.

بوابة القبول: استبدال محصل حصة واحدة يبقي بقية المستلمين وحصصهم؛ تعارض وصاية يعيد فشلاً دون حفظ جزئي؛ إصدار دفتر لا يلغي مستلمي باقي المستحقين.

### P3: الإيقاف والمراجعة والمعاملات

الملفات: `AgentService.cs` و`EntitledPersonService.cs` و`EntitlementEngine.cs` و`GuardianService.cs` و`FileReviewService.cs`.

- تعطيل/حذف الوكيل ينهي مستلميه بواسطة `AgentID`، مع `EndDate` وسبب الإنهاء وبيانات المدقق.
- إيقاف/وفاة/حذف/فقد أهلية المستحق ينهي مستلميه المباشرين ومستلمي جميع وكلائه، بما في ذلك المسار الآلي للعمر والزواج.
- إظهار تغيير المستحق في تفاصيل مراجعة الوكالة باسم المستحق قبل التغيير وبعده، بدلاً من استبعاد `EntitledID` على جميع أنواع السجلات. تبقى مفاتيح السجل الأساسية مستبعدة.
- طلب المراجعة جزء من نجاح العملية. فشله لا يعيد نجاحاً بعد حفظ تغيير غير مراجع؛ تتحقق حالات الملف قبل الكتابة وتفحص نتيجة الطلب.
- استخدام ملكية المعاملة القائمة: مالك المعاملة فقط يبدأ/يعتمد/يتراجع. يستعمل قفل صف الملف القائم `LockFileReviewAsync` قبل فحص التكرار والوصاية وحفظهما، لمنع تعارض طلبين متزامنين.
- ترتيب الأقفال في مسارات الكشف: قفل الكشف ثم الملفات بترتيب معرفاتها. عمليات الملف لا تستحوذ لاحقاً على أقفال كشوف بترتيب معكوس.
- تحفظ الآثار المالية والتدقيق والمراجعة معاً. الملفات الفيزيائية ليست جزءاً من معاملة SQL؛ يحدد لها تعويض عند فشل الحفظ، وتفصل نتيجة رفع المرفقات عن نتيجة إنشاء الوكالة.
- يبقى حفظ الوكالة مع فشل بعض المرفقات نجاحاً جزئياً واضحاً؛ يسجل النقص وفق نتيجة الرفع الفعلية، ويعرض للمستخدم ما يحتاج إعادة رفعه.

بوابة القبول: لا مستلم نشط لوكيل منتهٍ، ولا وكالة وصرف مستمران بعد وفاة المستحق، وتغيير الربط ظاهر في المراجعة، وفشل المراجعة لا يترك تغييرات أساسية محفوظة.

### P4: التوليد والاعتماد واستيراد النتائج

الملفات: `PayrollGenerationService.cs` و`SalaryPaymentBatchService.cs` وDTOs نتيجة التوليد.

- التحقق من الأهلية وصلاحية الوكلاء وتغطية جميع المستحقين والحصص قبل حساب أي بند للملف.
- تطبيق قرار حجب الملف كاملاً عند نقص مستلم. بقية الملفات المكتملة في الكشف لا تتأثر.
- فحص تواريخ بدء/انتهاء المستلمين بالنسبة لتاريخ الصرف المستعمل في التوليد، وعدم الاكتفاء بـ `IsActive`.
- إعادة فحص التغطية والمستلمين والحصص الحالية ومطابقتها لبنود المسودة قبل الاعتماد؛ تغيير النطاق أو المستلم أو المبلغ يتطلب إعادة التوليد. تبقى فحوص `ISoDGuard` والاعتماد المحاسبي القائمة لازمة.
- لا تعاد كتابة بنود الكشوف المعتمدة أو الحوالات المنفذة. تعالج تغييرات الأهلية اللاحقة وفق حالة العملية؛ لا يمحو حظر صرف جديد سجل نتيجة حوالة نفذت فعلاً.
- إضافة معرف ثابت لبند الصرف `PaymentItemID` إلى التصدير، واعتماده عند استيراد النتائج مع التحقق من انتمائه للكشف ومطابقة بيانات الملف.
- دعم الملفات القديمة التي تحوي رقم الملف فقط عندما يطابق بنداً وحيداً. عند تعدد البنود يرفض السطر برسالة تحدد حاجته لمعرف البند؛ لا يختار الأول.
- كشف تكرار معرف البند في ملف الاستيراد وتعارض هوية البند، وإظهار أخطاء الأسطر دون تعديل بند آخر.
- تحميل `Agent.EntitledPerson` صراحة عند التصدير، وعدم الاعتماد على تحميل كسول غير مهيأ.

بوابة القبول: ثلاثة مستلمين ينتجون ثلاثة بنود صحيحة؛ غياب أحدهم يحجب الملف؛ تغيير وكيل بعد التوليد يمنع اعتماد المسودة؛ استيراد ثلاث حوالات يحدث ثلاثة بنود مختلفة.

### P5: الواجهة والتقارير

الملفات: `ui/src/types/retirement.ts`، `AgentDialog.tsx`، `AgentsTab.tsx`، `ViewAgentDialog.tsx`، `AgentsPage.tsx`، `RecipientsTab.tsx`، `RecipientsDialog.tsx`، `SalaryRecipientFormDialog.tsx`، `api/salary-recipients.ts`، `sections/FinancialSection.tsx`، ومسارات الطباعة المتأثرة.

- إضافة اختيار واضح «الوكالة عن» بين الملف العام ومستحق معين، مستقل عن تعبئة بيانات الوكيل من شخص موجود.
- تحميل المستحقين وفق الصلاحية، وعرض حالات عدم الصلاحية أو التعارض دون اختيار نطاق بديل تلقائياً عند فشل التحميل.
- حفظ الربط في المسودة وطلبات الإنشاء والتعديل؛ الحفاظ عليه أثناء رفع الصورة وفي أحجام العرض المختلفة.
- إتاحة زر إضافة وكيل مع وجود وكلاء آخرين، ومنع اختيار النطاق المشغول مع بقاء تحقق الخادم هو المرجع.
- عرض «وكيل عام» أو «عن المستحق: الاسم» في الجدول والتفاصيل واختيار المستلم والطباعة. توحيد الأنواع بدلاً من التحويلات المزدوجة و`any` في المسار المعدل.
- عرض الحصة المستنتجة لصاحب الحساب، وحالة عدم اكتمال مستلمي الملف، وأسباب الاستبعاد القادمة من الخادم.
- إظهار تحذير حفظ الوكيل مع فشل المرفقات بدلاً من رسالة نجاح ثابتة.
- استعمال أدوات التاريخ المقررة وحقول التحميل الفعلية؛ معالجة JSON مقابل `FromForm` إن استعمل أي مسار قديم لإنشاء المستلم.
- توحيد مفاتيح تحديث cache: الوكلاء والبحث والمستحقون والمستلمون وملخص الملف والمراجعة والنواقص، بحسب أثر العملية.
- عرض جميع الوكلاء ذوي الصلة في المستحقات المالية بدلاً من `First()`؛ الحفاظ على شكل الاستجابة المتوافق أو إضافة قائمة واضحة واستهلاكها بالواجهة.
- الالتزام بالعربية وRTL والتوكنات القائمة والوضعين الفاتح والداكن، مع تحقق لوحة المفاتيح وشاشات الهاتف والحاسوب.

بوابة القبول: موظف يسجل وكلاء ثلاثة مستحقين ويعينهم للصرف ويفهم حصة كل منهم وحالة اكتمال الملف، دون فك روابط سابقة عند التعديل.

### P6: SQL والتطبيق المرحلي

- كتابة سكربت تصحيحي مستقل قابل لإعادة التشغيل في `scripts/`؛ لا تعديل مدمر للسكربت السابق ولا إنشاء EF Migration.
- الإبقاء على فهرس الوكلاء المرتبطين، وإضافة فهرس فريد مفلتر على `FileID` للوكيل العام النشط فقط: `EntitledID IS NULL AND IsActive = 1 AND IsDeleted = 0`.
- التحقق من وجود الفهرس الثلاثي لبنود الصرف فعلياً ومن إزالة الفهرس القديم الذي يمنع تعدد البنود. مقارنة تعريفات الفهارس، وليس أسمائها فقط.
- إيقاف السكربت برسالة واضحة عند وجود تكرارات تمنع القيود؛ إرفاق نتائج التشخيص بدلاً من حذف السجلات أو اختيار وكالة للفوز تلقائياً.
- تحديث إعدادات EF لتطابق SQL، وتوثيق آلية عودة التغيير دون فقد عمود الربط أو التاريخ المالي.
- التطبيق أولاً على قاعدة اختبار مماثلة للبيئة المستهدفة، ثم الكود والخادم والواجهة كإصدار متوافق. تستخدم سكربتات النشر الموجودة عند مرحلة التطبيق الفعلية.

بوابة القبول: طلبان متزامنان لنفس النطاق لا ينشئان وكالتين، وتشغيل SQL مرتين آمن، والبيانات السابقة ذات `EntitledID = null` تظل قابلة للقراءة.

## 6. الاختبارات المطلوبة

| المجموعة | السيناريوهات الأساسية |
|---|---|
| إنشاء الوكيل | عام، مرتبط، ثلاثة مستحقين، تكرار النطاق، مستحق من ملف آخر، محذوف/متوفى، وصاية قائمة |
| التعديل | الحفاظ على الربط عند غياب الحقل، فك صريح، رفض النقل بعد تاريخ صرف، تعارض التعديل، رفع الصورة وحدها |
| الفروع | بحث وقراءة وتعديل وحذف من الفرع الصحيح، منع الفرع الآخر، منع المستخدم بلا فرع، سماح المقر |
| الوصاية | المنع في اتجاهي التعيين، تعيين جماعي يفشل دون حفظ جزئي، منع مستحق ملف آخر |
| النطاق والحصة | استبدال محصل X دون إيقاف Y، عدم تصنيف وكلاء المستحقين كنطاق عام، نسخ حصة X، منع تكرار صرف X |
| الإيقاف | تعطيل/حذف الوكيل، حذف/وفاة/إيقاف المستحق، الزواج/العمر عبر المحرك، عدم إعادة التفعيل الضمني |
| دفتر الصرف | الإنشاء التلقائي يلتزم بالنطاق والحصة؛ فشل المستلم لا يحفظ دفتره أو يعطل دفتره السابق |
| التغطية | 50/30/20 مكتملة، غياب مستلم 20 يحجب الملف، وكيل مرفوض/منتهٍ يعد نقصاً، ملف آخر مكتمل يستمر |
| الحساب | لا تطبيع للحصص الناقصة، الحصص غير الصالحة تحجب الملف، التقريب حتمي، لا تجاوز للمعاش |
| المراجعة | تغيير المستحق وحده يولد بنداً باسمه، فشل المراجعة يعيد العملية، الوكيل أو المستحق المعلق لا يسمح بالصرف |
| الكشف | تغير المستلم/الحصة بعد التوليد يمنع الاعتماد، استمرار فحص SoD، عدم تعديل كشف معتمد تلقائياً |
| الاستيراد | معرف بند صحيح، بند من كشف آخر، بند مكرر، ثلاثة بنود لنفس الملف، ملف قديم وحيد ينجح، ملف قديم ملتبس يرفض |
| المرفقات | إنشاء جزئي مع تحذير ظاهر ونقص مسجل، إعادة رفع، فشل الصورة دون فقد الصورة السابقة |
| التواريخ | يوم الانتهاء وحدود منتصف الليل اليمني، UTC ووقت محلي وDateOnly، عدم تحريك اليوم أثناء التعديل |
| قاعدة البيانات | نموذج EF والفهارس وSQL المولد، طلبات متزامنة، إعادة تشغيل السكربت، بيانات قديمة |

تضاف اختبارات خدمات عبر xUnit وMoq وأنماط الاستعلام غير المتزامن القائمة. اختبارات ترجمة SQL وفحص النموذج لا تحتاج اتصالاً حياً. أما إثبات منع السباق والقيود الفعلية فيحتاج SQL Server في بيئة اختبار؛ لا يثبت عبر Moq وحده.

المشروع `PensionMS.Tests` لا يختبر Controllers أو ربط `multipart/form-data` أو الصلاحيات في خط HTTP. تضاف هذه التغطية داخل مشروع `PensionMS.IntegrationTests` القائم، وفق نمط استضافة HTTP في `AuthorizationHttpSqlTests`، واختبارات التزامن وفق `PayrollTransactionSqlTests`، واستكمال إيقاف الوكيل وفق `EligibilityAndPermissionSqlTests`. اختبارات SQL تتطلب `PENSIONMS_TEST_SQLSERVER` وتستخدم قواعد اختبار مؤقتة عبر `SqlTestDatabase`؛ لا تعرض قيمة الاتصال في المخرجات، ولا يوصف نجاح اختبارات الخدمات بأنها إثبات لاختبارات HTTP أو SQL التي لم تنفذ.

## 7. بوابات الإنجاز

1. بناء مشروع API وتشغيل `PensionMS.Tests` من مجلده، ثم اختبارات الميزة في `PensionMS.IntegrationTests` على SQL الاختبار، مع تحديث مواضع mocks المتأثرة بأي تغيير constructor.
2. للواجهة: مقارنة lint قبل/بعد، ثم `npm run build`، ثم `npm test`، ثم `npm run preview` والتحقق بالمتصفح. معيار lint هو عدم إضافة مشكلات جديدة.
3. تجربة متكاملة: ملف بثلاث حصص ووكلاء؛ قبل اكتمال المستلمين لا يصرف؛ بعد اكتمالهم تتولد البنود الصحيحة؛ استيراد الحوالات يحدث البنود المقصودة فقط.
4. إيقاف وكيل واحد يحجب الملف حتى تعيين البديل، ويحتفظ بتاريخ الصرف السابق ووكلاء بقية المستحقين.
5. تحقق من صلاحيات الفرع، والوصاية، والمراجعة، وتزامن التعيين، والفهارس على قاعدة الاختبار.
6. تحديث تقرير الميزة وحالة المراحل بنتائج التنفيذ الفعلية، ثم تجهيز التغييرات للمراجعة. لا تعتبر الخطة أو نجاح الاختبارات الحالية إكمالاً للميزة.

الترتيب: P0 ثم P1 ثم P2 وP3 ثم P4 ثم P5، مع تجهيز SQL في P6 مبكراً والتحقق من تطبيقه قبل اختبار التزامن والتسليم. لا تطلق واجهة التعدد للمستخدم قبل اكتمال حواجز الصرف والاستيراد.
