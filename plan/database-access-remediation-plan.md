# خطة إصلاح الوصول إلى قاعدة البيانات في PensionMS

التاريخ: 2026-10-09 بتوقيت اليمن.

الحالة: نُفذت إصلاحات الكود الأساسية واختُبرت على SQL Server ببيانات مصطنعة؛ آخر تحديث 2026-10-11. لم تُطبق سكربتات الفهارس على قاعدة المشروع. تفاصيل الأدلة والبنود المفتوحة في [تقرير التنفيذ](../docs/audits/database-access-remediation-results.md).

## الهدف والقرارات

إصلاح سلامة البيانات وصلاحيات القراءة أولًا، ثم تحسين الاستعلامات وفق القياس. تشمل الخطة جميع مجالات Infrastructure والخدمات والعقود والـ Controllers والاختبارات المرتبطة بالمسارات المتأثرة.

- الإبقاء على ASP.NET Core 8 وEF Core 8 وSQL Server وGeneric Repository وUnitOfWork والمستودع المتخصص الموجود للتسويات.
- لا إنشاء مستودع لكل كيان، ولا استبدال شامل للمعمارية، ولا إعادة تنظيم المجلدات مرة أخرى.
- الخدمة التي تنسق عملية العمل كاملة تملك Commit/Rollback. يمكن إجراء SaveChanges داخلي للحصول على Identity داخل المعاملة؛ الحفظ لا يساوي الالتزام.
- الإشعار وOutbox جزء من معاملة العملية؛ إرسال SignalR يبدأ بعد الالتزام عبر المعالج الخلفي.
- نطاق الفرع يُفرض من هوية موثوقة قبل العد والتجميع والتصدير. قيمة BranchId القادمة من العميل لا توسع الصلاحية.
- إصلاح مسارات الحذف المنطقي صراحةً؛ لا إضافة اعتراض عام يحول جميع عمليات DELETE بصمت.
- تغييرات المخطط عبر سكربتات SQL مدروسة وإعدادات EF المطابقة، دون الاعتماد على Migrations الفارغة.
- حفظ تعديلات نسخة العمل السابقة. كل دفعة تحتوي تغييرًا محددًا واختباراته وتوثيق تحققها.

## الأدلة وحدودها

المراجعة شملت 99 ملف Services؛ 96 صنفًا فريدًا، منها 90 خدمة/محرك/مزود بعد استبعاد ستة أصناف مساعدة. ReportService محسوبة مرة واحدة رغم ملفات partial. خصائص IRepository في IUnitOfWork عددها 119، وDbSet عددها 127. ملفات Jobs الثلاثة مستقلة عن هذا العد.

تم فحص قاعدة التطوير بقراءة فقط. النتائج التاريخية لا تمثل اختبار حمل للإنتاج:

لم تُرصد في البيانات الحالية حالات أحدث استحقاق منتهٍ لملف فعال، أو مستلم فعال لمستحق غير فعال، أو دفاتر فعالة متعددة للملف، أو إهلاك قبل بدء الخدمة. AttendanceEvents وDepreciationSchedules فارغان عند الفحص. العيوب المنطقية المرتبطة بهذه الحالات تُثبت باختبارات مخصصة، ولا تُوصف باعتبارها فسادًا وقع فعليًا.

الروابط أدناه تشير إلى ملفات الكود؛ أرقام الأسطر هي مرجع وقت المراجعة وقد تتحرك أثناء التنفيذ. الدالة ومعرّف المهمة هما مرجع التتبع المستمر.

## M0 — تثبيت خط الأساس وتجهيز التحقق

1. تسجيل حالة نسخة العمل والبناء والاختبارات الحالية دون تغيير تعديلات المستخدم السابقة.
2. تشغيل اختبارات PensionMS.Tests وبناء API من المشروع المحدد. العدد الأخير المعروف من إعادة التنظيم لا يُعامل باعتباره نتيجة تشغيل جديدة.
3. تسجيل مخطط وفهارس وإحصاءات الاستعلامات المستهدفة قبل تحسينها، مع تاريخ القياس وشكل المرشحات وعدد النتائج.
4. إعداد مشروع اختبارات منفصل مقترح باسم PensionMS.IntegrationTests، مبرره اختبار EF الحقيقي والمعاملات والتزامن ونقاط HTTP؛ مشروع الاختبارات الحالي لا يراجع API ولا يعتمد قاعدة فعلية.
5. استخدام قاعدة SQL Server مخصصة للاختبارات وبيانات مصطنعة فقط. إعداد اتصال صريح عبر متغير بيئة، والتحقق من اسم قاعدة الاختبار قبل أي تهيئة أو تنظيف. لا اتصال تلقائي بقاعدة التطوير أو الإنتاج.
6. تهيئة مخطط الاختبار من نموذج EF أو مخطط مخصص للسيناريو تحت الاختبار، بعد مقارنة القيود والفهارس المطلوبة. لا الاعتماد على Migrate لإنشاء baseline غير موجود.
7. احتساب الاستعلامات بواسطة interceptor داخل الاختبارات، دون إضافة تسجيل بيانات أشخاص إلى التشغيل الفعلي.

بوابة القبول: خط أساس قابل لإعادة التشغيل؛ الاختبارات الحالية تبقى مستقلة عن SQL Server. اختبارات التكامل لها أمر تشغيل مستقل، وفقد اتصالها المطلوب يمنع اعتبار تحقق SQL مكتملًا.

## M1 — فرض نطاق الفرع في القراءة والتقارير

الملفات: Services/Reporting/ReportService بجميع ملفاته، ReportDataService، RetirementFileReportService، DashboardService، وControllers/ReportsController وDashboardController والعقود/الاختبارات المتأثرة.

- تتبع كل مسار تقرير، وقائمة، وعدد، وملخص، وتصدير إلى الاستعلام الذي يجلب البيانات.
- استخدام IBranchScopeProvider الموجود: مستخدم الفرع يقرأ فرعه؛ HQ يمكنه قراءة الكل أو اختيار فرع.
- مستخدم غير HQ دون فرع صالح لا يحصل على نطاق مفتوح. طلب فرع خارج النطاق يُرفض باستجابة عربية واضحة.
- إذا كان المسار يدعم نطاق إقليم/عدة فروع بالفعل، تُشتق القائمة من تعيينات الصلاحيات الموثوقة الموجودة؛ لا تُستنتج من مرشحات العميل.
- تطبيق القيد على IQueryable قبل Count/Sum/GroupBy/Skip/Take، وعلى الكيانات المرتبطة بالملف أيضًا.
- تحديد الجداول المركزية التي لا تحمل نطاق فرع، مثل قوائم الدليل المرجعية؛ لا إلحاق مرشح وهمي بها.
- نقل استعلامات DashboardController وStocktakeController المباشرة إلى الخدمات الموجودة الملائمة، دون Repository جديد.
- تحديث المنشئات وتسجيلات DependencyInjection واختبارات mocks في نفس الدفعة.

الاختبارات: فرع A وفرع B، مستخدم A، HQ، مستخدم بلا نطاق؛ مرشح فرع آخر؛ الأعداد والصفحات والتصدير. إثبات تطابق سياسة النطاق بين PDF وExcel.

بوابة القبول: لا صفوف أو إجماليات من فرع B في مسارات مستخدم A؛ لا توسيع للنطاق عند غياب Claim؛ لا raw EF في الـ Controllers المتأثرة.

## M2 — ملكية المعاملة وإعادة توليد الرواتب وOutbox

تُنفذ كدفعات صغيرة بهذا الترتيب:

### M2.1 — عقد المعاملة

الملفات: Core/Interfaces/IUnitOfWork، Repositories/UnitOfWork، Accounting/JournalEntryService، الخدمات المنسقة المتأثرة.

- تثبيت نمط ownsTransaction باستخدام HasActiveTransaction. من يبدأ المعاملة فقط يلتزم بها أو يتراجع عنها.
- توحيد النمط في ReverseJournalEntryAsync ومسارات التكامل التي تبدأ معاملات دون مراعاة معاملة المستدعي.
- الإبقاء على عقد CommitAsync الحالي الواضح: الالتزام لا يحفظ التغييرات تلقائيًا.
- فشل الدالة الداخلية يمنع الخدمة الخارجية من الالتزام، سواء كان استثناءً أو ApiResponse فاشلًا.
- بعد Rollback لا يُستمر بحفظ ChangeTracker كما لو لم يحدث فشل. مسارات الاستيراد التي تتابع تستخدم نطاقًا مستقلًا للوحدة التالية أو معالجة محددة لحالة التتبع؛ لا Clear عام يفسد مراجع المستدعين.
- الحفاظ على فحوص الصلاحيات وSoD القائمة، ومراجعة القواعد المنطبقة على العمليات المالية المتأثرة دون اختراع معرف FileID لعملية لا تتبع ملفًا.

### M2.2 — إخطار مرتبط بالالتزام

الملفات: INotificationService، Notifications/NotificationService، Entities/NotificationOutbox والعلاقات الموجودة، Jobs/NotificationOutboxProcessor، PayrollGenerationService والمستدعون.

- إضافة مسار enqueue صغير في العقد الحالي إذا احتاجته العمليات المنسقة، دون خدمة أو Repository جديد لمجرد التغليف.
- هذا المسار يضيف Notification وOutbox دون SaveChanges أو SignalR. استخدام علاقة NotificationOutbox.Notification الموجودة لحفظ الاثنين معًا ومعالجة Identity بواسطة EF.
- جرد مستدعي SendNotification/NotifyRole/NotifyBranch داخل عمليات العمل وتحويلهم إلى مسار enqueue؛ لا يقتصر الإصلاح على الرواتب. منع الإرسال الفوري عند وجود معاملة خارجية نشطة.
- المحافظة على عمل طلب إرسال إشعار مستقل: يملك حفظه والتزامه عندما لا يكون جزءًا من عملية أخرى.
- معاملة العملية الأكبر تحفظ صفوفها والإشعار وOutbox معًا. المعالج الخلفي يرسل الصفوف الملتزمة.
- توثيق أن Outbox يوفر إعادة محاولة وقد يعيد الإرسال عند توقف العملية بين الإرسال وتحديث الحالة؛ لا ادعاء exactly-once. NotificationID يتيح التعامل مع تكرار الحدث.

### M2.3 — إعادة توليد الرواتب

الملفات: Payroll/SalaryPaymentBatchService وPayrollGenerationService وIPayrollGenerationService.

- GenerateItemsAsync تملك المعاملة والتسلسل: قراءة الكشف وقفل مناسب له، التحقق من Draft، استبدال البنود، تحديث الإجماليات، enqueue، حفظ والتزام.
- المولد يُرجع البنود والنتائج دون إضافتها أو حفظها أو إرسال إشعار. الخدمة الخارجية تضيفها مرة واحدة.
- التمييز صراحةً بين إعادة بناء الكشف ومنع التكرار عند الاستكمال؛ لا استعلام يعيد البنود المستبدلة ويمنع بناء بدائلها.
- القفل على مستوى قاعدة البيانات ومعاملة الكشف يمنعان طلبَي توليد متزامنين من اجتياز Draft معًا؛ لا الاكتفاء بـ Semaphore داخل العملية.
- لا فهرس فريد على BatchID/FileID وحدهما، لأن الملف يمكن أن يحمل عدة مستلمين.
- فشل التوليد أو الحفظ يعيد البنود القديمة والإجماليات كما كانت، ولا يترك إشعار اكتمال.

## M3 — تسلسل التدقيق مع حفظ التاريخ

الملفات: Audit/ImmutableAuditService، IImmutableAuditService عند الضرورة، إعداد اختبارات SQL، ووثيقة نتائج فحص مستقلة.

- استخدام قفل SQL Server مشترك، مثل sp_getapplock بوضع Exclusive وLockOwner=Transaction، حول قراءة آخر Hash والإضافة.
- LogAsync تشارك في المعاملة الحالية؛ تملك معاملة خاصة عندما لا توجد واحدة. القفل لا يتحرر قبل انتهاء المعاملة.
- فحص رمز عودة القفل ومعالجة انتهاء المهلة/الفشل صراحةً؛ لا متابعة الإضافة دون القفل.
- الحفظ الداخلي المطلوب لتثبيت السجل لا يلتزم بمعاملة المستدعي. تثبيت ترتيب الحصول على الأقفال وفحص احتمال deadlock بين سجلات العمل وقفل التدقيق.
- لا تغيير لصيغة ComputeHash الحالية في هذه الدفعة؛ تغيير الصيغة يحتاج versioning مستقلًا.
- اختبار CreatedAt بعد دورة حفظ وقراءة فعلية: DateTime.Kind ودقة القيمة وتمثيلها بصيغة O يجب ألا ينتج عنها اختلاف في مادة التجزئة. إذا كشف الاختبار اختلافًا، يُحدد توافق القراءة مع الصيغة التاريخية قبل اعتماد الإصلاح، دون إعادة Hash للسجلات.
- التحقق بقراءة ثابتة أو حد أعلى محدد أثناء فحص السلسلة حتى لا تتغير مجموعة السجلات وسط الفحص.
- حفظ تقرير منفصل عن الروابط التاريخية المكسورة دون إعادة Hash أو حذف أو إعادة ترتيب للسجلات.
- لا إضافة Unique على PreviousHash فوق البيانات الحالية المكررة.

الاختبارات: سياقات متعددة وكتابات متزامنة، معاملة خارجية تلتزم/تتراجع، انتهاء مهلة القفل، البداية الفارغة، فجوات Identity الناتجة عن Rollback، والتحقق من تجزئة المحتوى إضافة إلى ترتيب الروابط.

بوابة القبول: سلسلة جديدة سليمة بالكامل في قاعدة الاختبار؛ الإضافات إلى السلسلة الحالية ترتبط برأسها الصحيح ولا تزيد التفريع. معالجة التاريخ قرار منفصل؛ بقاء الخلل التاريخي لا يُخفى بتحويل اختبار السلامة إلى نجاح.

## M4 — صحة قواعد الصرف والاستحقاق والإهلاك

### M4.1 — الاستحقاق المالي

الملفات: PayrollGenerationService وFinancialEntitlementService وCore/Time/YemenTime.

- شرط الصلاحية يشمل EffectiveDate وEndDate، بحد نهاية شامل وفق العقد التقويمي الموجود.
- تحويل لحظة runAt إلى تاريخ اليمن بالوسائل الحالية عند الحاجة؛ لا مقارنة نهاية يوم تقويمي بلحظة UTC على نحو يستبعد اليوم نفسه.
- اختيار أحدث استحقاق صالح بترتيب حاسم عند تعادل EffectiveDate.
- لا تغيير تعريف تاريخ صرف كشف سابق/لاحق ضمن هذا الإصلاح دون دليل من قواعد العمل الحالية.
- اختبار اليوم السابق للبدء، يوم البدء، يوم الانتهاء، اليوم التالي، EndDate=null، منتصف الليل في اليمن، ووجود استحقاقات متعددة.

### M4.2 — المستحق والجهات التابعة

الملفات: EntitlementEngine وEntitledPersonService وSalaryRecipientService والمستدعون.

- ضبط حالة المستحق والوكلاء والمستلمين المرتبطين ثم حفظها ضمن العملية نفسها.
- إزالة الاعتماد على SaveChanges من خدمة تالية. تأكيد السلوك عندما يرجع المستدعي بفشل بعد إعادة التقييم.
- الحفاظ على قواعد الإيقاف اليدوي والوفاة والمراجعة؛ عدم إعادة تفعيل جهات مرتبطة دون قاعدة قائمة.

### M4.3 — الإهلاك وعدد الاستعلامات

الملفات: Assets/FixedAssetService وإعداد DepreciationSchedule الحالي.

- استبعاد الفترات التي تسبق InServiceDate، واختبار سنة سابقة وشهر سابق وشهر البدء وسنة تالية.
- الحفاظ على قاعدة الإهلاك الجزئي الحالية وسقف AcquiredCost-SalvageValue؛ اختبار الأصل الذي استُهلك بالكامل.
- تحميل مفاتيح الإهلاك للسنة والأصول المطلوبة مرة واحدة إلى HashSet بدل AnyAsync لكل أصل وشهر.
- الحفاظ على الفهرس الفريد AssetID/PeriodYear/PeriodMonth. معالجة التزامن بفشل واضح/إعادة محاولة للعملية كاملة؛ الفهرس وحده لا يحل تحديث قيم الأصل المتزامن.

بوابة القبول: لا صرف لاستحقاق منتهٍ، ولا تعطيل غير محفوظ، ولا إهلاك قبل بدء الخدمة؛ قراءات حساب الإهلاك ثابتة بالنسبة لعدد الأصول مع استثناء تقسيم قائمة معرّفات كبيرة عند الحاجة.

## M5 — الحذف المنطقي ومرجع الموارد البشرية

الملفات: Repository/IRepository، MissingDocumentService، DocumentExemptionService، InventoryItemService، InventoryCustodyService، FixedAssetService، UserService، HrAttendanceService، والعلاقات المتأثرة.

- جرد كل Delete/DeleteRange/Remove/RemoveRange على مستوى المشروع، وتصنيف الكيان والعلاقات قبل تعديل المسار.
- استبدال الحذف الفعلي للكيانات ISoftDeletable بتحديث IsDeleted/DeletedAt/DeletedByUserID حسب نموذج الكيان، مع الحفاظ على قواعد منع الحذف.
- حذف المستخدم يحتاج تعطيل تسجيل الدخول وإبطال التوكنات/الأجهزة والحفاظ على مراجع التدقيق؛ لا يكفي ضبط IsDeleted وحده.
- حصر الحذف الفعلي في الكيانات والمسارات المسموح بها. توضيح عقد IRepository، وإضافة منع صريح للحذف الفعلي على ISoftDeletable بعد إصلاح المستدعين؛ لا تغيير صامت للسلوك.
- في تسجيل الحضور: الحصول على Identity ثم تسجيل SourceEntityId الصحيح داخل معاملة واحدة. علاقة EF جديدة ليست لازمة إن كفى الحفظ المرحلي.

الاختبارات: السجل يبقى فعليًا ويختفي بالفلتر العام، IgnoreQueryFilters يعيده، العلاقات التاريخية تبقى، مستخدم محذوف لا يجدد جلسة، وفشل حفظ سجل خدمة الحضور يتراجع عن الحضور أيضًا.

بوابة القبول: لا DELETE فعلي على الكيانات المفحوصة القابلة للحذف المنطقي؛ SourceEntityId يشير إلى الحضور المحفوظ.

## M6 — اكتمال التقارير وصحة التسويات

### M6.1 — التصدير

الملفات: ReportDataService، ملفات ReportService الستة، Reporting/Exporters، ReportsController والعقود عند الضرورة.

- توحيد مجموعة البيانات والنطاق والمرشحات بين العرض وPDF وExcel.
- القراءة على دفعات بترتيب ثابت وفريد؛ لا الاكتفاء بالصفحة الأولى أو int.MaxValue.
- لا اعتبار الدفعات ضمانًا لذاكرة محدودة إذا كان exporter يجمع object[] كاملًا. قياس الحجم والذاكرة، وتحديد حد تشغيلي معلن أو تقسيم المخرجات عند الحاجة.
- عند تجاوز حد إخراج معتمد: خطأ عربي واضح أو إخراج مجزأ معلن؛ لا تسليم ملف ناقص باعتباره كاملًا.
- اختبار 10,001 نتيجة، وحدود تصدير أكبر، وعدم التكرار عند تعادل CreatedAt؛ مقارنة عدد وصفوف PDF وExcel دون الاعتماد على شكل الملف فقط.

### M6.2 — التسويات

الملفات: SettlementRepository، SettlementService، StringHelpers، ISettlementRepository، إعدادات SettlementItem، واختبارات التسويات الموجودة.

- إصلاح تصدير الرتب والراتب باستخدام قراءة DTO الموجودة المناسبة، وتكييف المستدعي دون إنشاء Repository آخر.
- في GetByRetireeIdAsync: إسقاط متطابق لجميع طرق الارتباط، يشمل DecisionNumber؛ اختبار RetireeID وApprovalItemID والرقم العسكري كلًا على حدة.
- توحيد تطبيع الأرقام العربية والفارسية والفراغات، مع حفظ الأصفار البادئة. لا تحويل الرقم إلى عدد.
- قبل عمود تطبيع جديد: فحص طول/صيغة الرقم ومصدره بين SettlementItem وApprovalItem، والتكرارات. المطابقة العسكرية لا تُفترض معرفًا فريدًا ولا تُحوّل إلى قيد Unique.
- إذا اعتُمد عمود NormalizedMilitaryNumber: تحديث نموذج EF والحفظ، backfill مدروس، فهرس غير فريد، ثم تحويل البحث إلى SQL. تجنب فقد المطابقات أثناء الانتقال؛ لا إزالة fallback قبل اكتمال التهيئة.
- إعادة صياغة إسقاط القرارات لتقليل الاستعلامات الفرعية المتكررة، وتحديد سياسة صريحة للكشف المختار بدل First غير المرتب.
- GetBatchDecisionsAsync تختار معلومات الكشف المطلوب نفسه؛ اختبار قرار متعدد الكشوف ببيانات مصطنعة.
- ترتيب الصفحات بمفتاح فريد إضافي، والتحقق من page/pageSize بما يتوافق مع عقود المشروع.
- ApplyRetireeRankUpdatesAsync تستخدم Dictionary وتعدل الكيانات المتتبعة دون Update زائد. نقل ملكية الالتزام إلى الخدمة المنسقة؛ إعادة تقييم الحفظ الداخلي بحسب حاجتها للمعرّفات والمعاملة.

بوابة القبول: نتائج الروابط المتنوعة كاملة، تصدير الرتب صحيح، حدود الصفحات ثابتة، والتصدير لا يقتطع نتائج بصمت. اختبار SQL وعدّ صفوف المرشحين يثبت أن البحث العسكري لا يحمل الجدول كله بعد تهيئة الحل.

## M7 — تحسين الاستعلامات والفهارس بالقياس

يمكن تقديم إصلاح فهارس التدقيق بعد M0 واكتمال فحص المخطط، دون انتظار تحسينات P2. ترتيب الاستعلام/نطاقه يُثبت قبل اختيار الفهرس النهائي.

### تغييرات الكود

- SimpleStocktakeService: تحميل البنود لكل قائمة الجرد مرة واحدة أو إسقاط SQL مناسب.
- NotificationOutboxProcessor: تحميل إشعارات الدفعة مع العلاقات المطلوبة دفعة واحدة؛ العدد يبقى محدودًا بثابت، لا عنصرًا عنصرًا.
- DiscrepancyService: تنفيذ Count/GroupBy في SQL قبل تحميل صفوف الملخص.
- ScopedPermissionResolver: استعلام الصلاحية المطلوبة مع الحفاظ على أولوية السحب الفردي ونطاق الفرع/الإقليم والقواعد القائمة. لا cache عابر للطلبات دون سياسة إبطال.
- مراجعة استعلامات FileQueryService والرسوم الكبيرة في المستحقين والوكلاء وفق الخطط. لا AsSplitQuery عام ولا حذف Includes عشوائي؛ الإسقاط إلى DTO أولًا حيث يناسب المسار.
- DashboardService: دمج إحصاءات الجدول نفسه إذا قلل الرحلات فعلًا؛ لا Task.WhenAll على DbContext مشترك.

### مرشحات الفهارس

| الجدول | الفهرس المرشح | شرط التنفيذ |
|---|---|---|
| AuditLogs | TableID, RecordID, CreatedAt DESC | تأكيد مسارات المساواة/قائمة RecordID والتاريخ؛ قياس خطة FileReview/GetByRecord |
| AuditLogs | CreatedAt مع LogID كترتيب حاسم، INCLUDE محدود لـ TableID/UserID/Action | توحيد اتجاه ترتيب الكود؛ لا تضمين OldValues/NewValues وحقول MAX لتغطية كل شيء |
| EntitledPersons | FileID بفهرس يخدم جميع الصفوف المطلوبة | تأكيد عدم وجود فهرس مكافئ؛ الحالي FileID/NationalID مفلتر لا يغطي كل مستحقي الملف |
| SettlementItems | NormalizedMilitaryNumber | بعد قرار M6.2 وتهيئة العمود والتحول إلى مقارنة SQL |
| SettlementItems | مفتاح القرار وترتيب البنود | بعد إعادة كتابة الإسقاط وقياس خطة الصفحة؛ لا اعتماد التصميم قبل ذلك |

لا فهارس إضافية افتراضية لـ FinancialEntitlements أو AttendanceEvents أو DepreciationSchedules أو UserRoleAssignments؛ توجد فهارس مفيدة بالفعل. تحسين Outbox يبدأ بعدد الاستعلامات، لا بإضافة فهرس تلقائيًا.

لكل فهرس معتمد: سكربت precheck ثم apply ثم rollback في scripts، وأسماء محددة وفحص التكافؤ لا الاسم فقط؛ إعداد EF مطابق. تطبيق على اختبار ثم بيئة قياس، وقياس قراءات SQL والزمن وعدد النتائج وكلفة الكتابة. لا SQL ONLINE=ON مفترض على نسخة Express.

بوابة القبول: النتائج لا تتغير؛ عدد قراءات N+1 يصبح ثابتًا؛ مقارنة الخطط والقراءات لنفس المرشحات. لا نسبة تحسن مضمونة ولا اعتماد زمن Query Store التاريخي وحده كقياس بعد التغيير.

## M8 — ضبط العقود دون تغيير شامل

الملفات: IRepository/Repository، IUnitOfWork/UnitOfWork، الخدمات التي تستخدم Update على رسوم محملة، DI، ووثائق المعمارية.

- توثيق التتبع وSave/Commit/Rollback والحذف والترتيب في العقود القائمة.
- إزالة Update الزائد من المسارات التي ثبت تتبع كياناتها؛ إبقاء تحديث الكيان المنفصل صريحًا ومحدودًا.
- دوال Pagination العامة غير المستخدمة: توثيق شرط ترتيب فريد، ثم اختيار تعديل العقد أو إزالة الدالة فقط بعد تأكيد عدم وجود مستدعين. لا توسيع API افتراضيًا.
- توثيق الاستخدامات المباشرة لـ DbContext المبررة، ومعالجة خلط السياق وUoW عندما ينتج حفظًا غير واضح؛ لا تغليف شكلي بمستودعات.
- عدم تفكيك واجهة UoW ذات 119 خاصية دفعة واحدة. يُضيق اعتماد مجال محدد فقط عندما يقدم التغيير منفعة قابلة للاختبار.
- Citizen غير المسجلة وPledgeExpiryCheckerService غير المسجل يبقيان خارج قياسات التشغيل. لا تفعيل أو حذف هذه المسارات ضمن إصلاح الأداء.
- Administration والقوائم المرجعية الصغيرة لا تحصل على Pagination أو cache دون مشكلة مقاسة.

بوابة القبول: عقود واضحة، لا تغييرات غير لازمة في HTTP أو أسماء الصلاحيات أو مفاتيح التقارير، وكل تغيير منشئ مغطى بتحديث mocks وفحص DI.

أوامر التحقق من جذر المشروع باستخدام ملف المشروع صراحةً:

```powershell
dotnet build .\PensionMS.API\PensionMS.API.csproj --nologo
dotnet test .\PensionMS.Tests\PensionMS.Tests.csproj --nologo
```

بعد إنشاء مشروع التكامل المقترح، يُشغل في بيئته المخصصة:

```powershell
dotnet test .\PensionMS.IntegrationTests\PensionMS.IntegrationTests.csproj --nologo
```

- اختبارات Moq تثبت قواعد العمل وعقود الفشل؛ اختبارات SQL تثبت الترجمة والتتبع وIdentity والمعاملات والتزامن. InMemory أو LINQ على List ليس بديلًا عن SQL Server لهذه الحالات.
- التغييرات في API تحتاج اختبار مسار HTTP/هوية/سياسة عند تأثيرها على النطاق أو الاستجابة، لأن المشروع الحالي لا يختبر هذه الطبقة.
- أرقام الأسطر تُحدث في سجل التنفيذ عند تغيرها؛ كل Rxx يرتبط بتغيير واختبار ونتيجة قبل/بعد.
- لا تشغيل اختبارات مالية أو حذف على قاعدة التطوير الفعلية، ولا تطبيق SQL ضمن مرحلة إعداد الخطة.
- لا عمل UI مطلوب افتراضيًا. إذا تغيرت استجابة أو واجهة فعلًا، تُطبق بوابات lint بالمقارنة مع baseline ثم build/test والتحقق المرئي بحسب AGENTS.md.

## ترتيب التنفيذ ومعايير الإغلاق

المسار الأساسي: M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8. فهارس التدقيق يمكن تقديمها بعد M0 وفق شروط M7. تُراجع وتُتحقق كل دفعة فرعية قبل توسيع التغيير.

الإغلاق يتطلب:

1. اختبارات تمنع رجوع R01–R10 وR20، مع إثبات SQL للمعاملات والتزامن.
2. تقارير وتصدير كاملان أو حد معلن، ونتائج تسويات صحيحة بمختلف الارتباطات.
3. نتائج قبل/بعد للاستعلامات والفهارس التي تم تغييرها، دون خلط Query Store التاريخي بقياس جديد.
4. توثيق الخلل التاريخي في سلسلة التدقيق وحالته منفصلًا؛ لا إعلان سلامة تاريخية لم تتحقق.
5. قائمة المهام المؤجلة والمشروطة واضحة، ولا تُحوّل إلى إصلاحات منفذة لمجرد تحسن التصميم.

إصلاح السجلات التاريخية، وتطبيق سكربتات الإنتاج، والنشر خطوات مستقلة بعد التحقق من التغييرات والسكربتات الملموسة. إعداد هذه الخطة لا ينفذ أيًا منها.
