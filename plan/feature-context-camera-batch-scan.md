## Problem Statement

الموظف يصور الوثائق لقطة-لقطة: فتح كاميرا ← تصوير ← قص يدوي بأربع زوايا ← قبول، مع تكرار لكل ورقة. لا يوجد كشف تلقائي للحواف، ولا فحص جودة (ضبابية/لمعان/قص ناقص)، ولا منع تكرار داخل الجلسة قبل الرفع.

**Evidence**: `ui/src/components/ui/FileUploader.tsx:392-418` — `capturePhoto` لقطة واحدة ثم `setCropOpen(true)` يدويًا؛ `ui/src/components/ui/CornerEditor.tsx` — تصحيح يدوي فقط؛ `docs/audits/document-flow-audit-2026-09-29.md:218-232` — التكرار يعتمد الاسم/الحجم و`X-Request-Id` للتسجيل فقط؛ `PensionMS.Infrastructure/Services/DocumentService.cs:447-464` — منع التكرار الحقيقي (SHA-256 + نطاق مالك) موجود في الخادم فقط بعد الرفع.
**Frequency**: كل ملف تقاعد يستقبل عدة وثائق؛ كل وثيقة = دورة تصوير + قص يدوية.
**Impact**: وقت أطول، صور رديئة تُقبل دون تنبيه، وخطر اعتبار 409 نجاحًا لوثيقة تخص شخصًا آخر (`BulkUploadDialog.tsx:763-781`).

## Core Intent Analysis

### WHO (Target Users)
موظف فرع/أرشيف يرقمن وثائق ملفات التقاعد — **الأساس: بهاتف محمول** (قرار المستخدم). ظروف إضاءة وعدسات متنوعة وموارد محدودة.

### WHAT (Desired Outcome)
جلسة تصوير متتالية واحدة: صوّر ← تنبيه جودة (لا منع) ← أضف للقائمة ← صنّف لاحقًا (النوع/الصاحب) ← ارفع عبر المسار الحالي.

### WHEN (Trigger Conditions)
عند استلام حزمة أوراق ورقية لملف (إضافة وثائق أو استكمال نواقص) من `DocumentsTab` ← `BulkUploadDialog`.

### WHY (Problem Being Solved)
تقليل إعادة التصوير والرفض اللاحق، وتقليل الأخطاء اليدوية (قص خاطئ، نسيان تصنيف، فقدان صور)، مع تنبيه مبكر للجودة دون تعطيل العمل.

## تعديلات مثبتة (R1–R3)

### R1: منع التكرار = قفل حدث + حالة انتظار (بلا مقارنة محتوى)
- `captureId` لكل محاولة و`sessionId` للجلسة لمنع التزامن والنتائج المتأخرة.
- بعد كل التقاط: دخول حالة انتظار وتعطيل Auto Capture. لا إعادة تفعيل بمؤقت.
- إعادة التفعيل فقط بعد التأكد من إزالة الوثيقة الحالية من الإطار ثم ظهور وثيقة جديدة مستقرة.
- فقدان المضلع لحظيًا (يد/تركيز) لا يعد إزالة. دوران نفس الورقة وإعادتها يقبل كعنصر جديد بلا تحذير — مقبول في هذه المرحلة.

### R2: فصل شروط Auto Capture عن تقييم الجودة
- Auto Capture يشترط فقط: وثيقة مكتشفة بشكل كافٍ (مضلع صالح داخل الإطار) + ثبات مقبول (حركة زوايا ومحتوى ضمن عتبة خلال نافذة).
- الضبابية والإضاءة واللمعان والتباين والضوضاء **لا تمنع** الالتقاط ولا الإضافة للقائمة — تسجل كتنبيهات جودة فقط.
- الوثيقة ذات شارة "تحتاج مراجعة" يجب تأكيدها بشريًا قبل الرفع النهائي (قرار Q2 يبقى).

### R3: لا 409←نجاح قبل التحقق (نتائج الفحص)
- مصدر 409 الوحيد في الرفع: `DuplicateDocumentException` من `DocumentService.cs:464` ← رد `DocumentsController.cs:188-196` مع `Data` = الوثيقة المطابقة كاملة (مالك + نوع + ملف + `EntityName`، انظر `MapToDto:1341-1390`).
- استعلام المطابقة منحصر بالنطاق: `FileID` + `DocumentTypeID` + IDs المالك + (`Checksum` أو احتياطي الاسم/الحجم عند `Checksum` null) — `DocumentService.cs:447-458`.
- الخلل المؤكد في الواجهة: `BulkUploadDialog.tsx:763-778` يعد أي 409 مع `documentID` نجاحًا بلا مقارنة مالك/نوع/ملف.
- خطر إضافي: المالك الافتراضي الصامت `"retiree"` (`BulkUploadDialog.tsx:582`) يرسل بلا ID شخص صريح؛ أي خطأ مستخدم في اختيار الصاحب يُقنّع كنجاح عند التطابق مع النطاق المطلوب.
- القاعدة الملزمة: لا قبول 409 كنجاح إلا بعد مطابقة `FileID` + `DocumentTypeID` + IDs المالك بين الرد والطلب؛ عند عدم المطابقة يعرض خطأ يذكر المالك الحقيقي (`EntityName`/`EntityType`) ولا يسجل نجاحًا. Q3 (تصنيف صريح إجباري) يغلق الثغرة من الأمام.

## Goals (مثبتة — Q1–Q3 + R1–R3)

1. جلسة هاتف واحدة لتصوير دفعات بكشف محلي + قص، مع قفل حدث صريح (`captureId`/`sessionId`) وحالة انتظار حتى إزالة الورقة وظهور جديدة (R1).
2. Auto Capture بشرطين فقط: مضلع كافٍ + ثبات مقبول. تنبيه جودة عربي (حدة/إضاءة/لمعان) كشارة مراجعة — قبول دائمًا، تأكيد بشري إجباري قبل الرفع (R2 + Q2).
3. قائمة مراجعة بمصغرات وعدّاد + حذف/إعادة تصوير يدوية؛ لا مقارنة محتوى تلقائية.
4. تصنيف صريح إجباري (نوع + صاحب) ثم رفع عبر المسار الحالي؛ 409 لا يقبل نجاحًا إلا بمطابقة `FileID`/النوع/المالك مع عرض المالك الحقيقي (R3 + Q3).
5. إصلاح الإلغاء/التحقق الحالي (دلالة الإلغاء، فشل التحقق يبقي المحرر مفتوحًا) دون كسر الرفع العادي والماسح.
