# خطة إصلاح الإشعارات

التاريخ: ١١ أكتوبر ٢٠٢٦، توقيت اليمن.

الحالة: خطة جاهزة للتنفيذ، لم تبدأ مراحل الإصلاح. مرجعها [تقرير التدقيق](../docs/audits/notification-mechanism-audit.md) وأدوات إعادة الإنتاج الموجودة. الأرقام N01–N16 تشير إلى نتائج التقرير، وليست أسماء مراحل التنفيذ.

## الهدف

حفظ إشعارات الأعمال مع معاملاتها، إيصال السجل الصحيح للمستخدم عند الدخول والعودة من الانقطاع، وإظهار تنبيه لحظي واحد للحدث الجديد. توحيد حالة القراءة والعدد، وحماية الحذف والمرفقات، ومعالجة ازدحام الإرسال وتعدد نسخ الخادم دون فقد البيانات أو الادعاء بأن محاولة البث تعني الاستلام.

## القرارات الأساسية

| المجال | القرار |
|---|---|
| سجل الإشعارات والعدد | بيانات خادم تُدار عبر TanStack Query؛ الجرس والصفحة يستخدمان نفس مفاتيح الاستعلام. |
| التنبيه العائم | طابور أحداث مستقل في Zustand، مرتبط بالمستخدم والجلسة. جلب السجل لا يضيف تنبيهات. |
| العدّاد | قيمة موثوقة من الخادم، مستقلة عن عدد العناصر في الصفحة. أحداث SignalR تسبّب إعادة الجلب المجمعة؛ لا يجتمع خصم محلي مع عدد مدفوع من الخادم. |
| الاستعادة | جلب عند كل جلسة صالحة، وعند الاتصال وإعادة الاتصال وعودة التركيز. أثناء انقطاع SignalR، إعادة جلب كل ٣٠ ثانية ما دامت الصفحة مرئية؛ لا طلبات دون مستخدم صالح. |
| التكرار | منع تكرار التنبيه والصوت بمعرّف الإشعار داخل الجلسة، مع السماح بتحديث محتوى إشعار موجود. إعادة جلب السجل لا تعتبر وصولًا لحظيًا. |
| معاملات الأعمال | تجهيز Notification وOutbox داخل معاملة العمل؛ يملك المنادي الحفظ والتثبيت. البث يتم خارج المعاملة. |
| تسليم Outbox | يمكن تكرار البث بعد إخفاق أو إعادة تشغيل. يكون الاستقبال قابلًا للتكرار دون آثار مكررة؛ حجز العامل يمنع المعالجة المتزامنة المعتادة، ولا يُقدَّم ضمان «مرة واحدة» عبر الشبكة. |
| معنى Sent | «تم البث»/«اكتملت محاولة الإرسال»، وليست «استلمه المستخدم». حالة القراءة تبقى منفصلة. لا حاجة لإضافة بروتوكول تأكيد استقبال لإصلاح المشكلات الحالية. |
| المرفقات | تنزيل عبر API مصادق عليه يتحقق من ملكية الإشعار، ثم Blob من الواجهة. تُغلق مسارات الوصول القديمة التي تتجاوز التحقق. |
| مخطط قاعدة البيانات | تغييرات إضافية صغيرة، بإعدادات EF وسكربتات SQL يدوية وفحص سابق وخطة تراجع. |

يُحافظ على مدة البطاقة الحالية: ٧ ثوانٍ مع إيقاف المؤقّت عند مرور المؤشر، وحد أقصى ٣ بطاقات مرئية. تُعرض بقية الأحداث من الطابور تباعًا، مع حد ذاكرة واضح وتجميع الفائض في تنبيه عربي؛ السجل الكامل يبقى محفوظًا في الخادم.

يكون الإغلاق مجرد إخفاء للبطاقة. فتح إشعار من أي سطح يستخدم وجهة مشتركة ويحدّث القراءة بعد نجاح الخادم. إشعار إنشاء الملف يفتح تفاصيل الملف المرتبط. التنبيه العائم هو سطح العرض لأحداث الإشعارات؛ تبقى رسائل نجاح النماذج تأكيدًا للعملية، ويُمنع إظهار بطاقة ثانية لحدث تأكيد ذاتي مطابق عبر معرّف العملية عند توفره، دون مقارنة نصوص الرسائل.

## التسلسل وحجم الدفعات

تُنفَّذ NF0 ثم NF1 ثم NF2 ثم NF3 ثم NF4 ثم NF5 ثم NF6. كل مرحلة تُقسَّم إلى تغييرات صغيرة قابلة للمراجعة، ويُحدّث تقرير التدقيق بدليل الإغلاق. لا يُغلق بند لمجرد تغيير الكود أو نجاح اختبار تشخيصي يؤكد السلوك القديم.

| المرحلة | الناتج | أهم النتائج المغطاة | المخطط |
|---|---|---|---|
| NF0 | أساس تحقق حديث واختبارات تكشف الانحدار | جميع البنود | لا تغيير |
| NF1 | حراس الحذف والجلسة والمرفقات | N03، N13، ملكية المرفق | غالبًا لا تغيير |
| NF2 | مصدر موحد للسجل والقراءة، وطابور عائم صحيح | N01–N09، N15، N16، اختلاف النقر والقراءة | لا تغيير أساسي |
| NF3 | مستلمون صحيحون وإشعارات داخل معاملة الأعمال | N14، الإشعار بعد Commit، نطاق الفرع | لا تغيير إلا إذا اقتضت سياسة المستلمين |
| NF4 | حجز متين للمعالج وإرسال قابل للاستعادة | N10–N12، N15، تراكم Outbox | حقول حجز وفهارس محسوبة |
| NF5 | تنزيل ورفع صحيحان، ووقت وإحصاءات متسقة | المرفقات، الإحصاءات، عقد التاريخ | حسب الفهارس المثبتة بالقياس فقط |
| NF6 | تحقق كامل وتجهيز النشر والتراجع | جميع البنود | تطبيق مدروس للتغييرات المعتمدة |

## NF0 — تأسيس التحقق

- حفظ لقطة جديدة لحالة ملفات الإشعارات ومخرجات lint والبناء والاختبارات؛ توجد تغييرات سابقة واسعة في نسخة العمل، فلا تُستبدل أو تُلغى.
- إعادة التحقق من بناء `PensionMS.Tests` و`PensionMS.API`. كان التدقيق السابق متوقفًا عند `OfficeProperties.Description`، لكن القراءة الحالية لا تُظهر هذا السطر؛ لذلك يُعاد الاختبار ولا يُعامل العائق القديم كحقيقة حالية. إذا بقي عائق مستقل، يُسجَّل موقعه ويُفصل عن نتائج إصلاح الإشعارات.
- تحويل الحالات التشخيصية إلى اختبارات انحدار تتوقع السلوك المطلوب. اختبارات مثل «حذف الطلب الفارغ لجميع الإشعارات» يجب أن تتوقع الرفض وصفر حذف. اختبار عدم وجود اتصالات يستمر في التحقق من معنى البث، ويُضاف له اختبار استعادة السجل للمستخدم.
- إضافة اختبارات منطق الحالة في `ui/tests/notifications.test.ts`، واختبارات المتصفح للمؤقّت وStrictMode وترتيب HTTP/SignalR، بالاعتماد على المكوّنات الفعلية. لا يُستعاض عنها بمحاكاة React مبسطة في مسائل دورة الحياة.
- إضافة اختبارات خدمات في `PensionMS.Tests/Services/NotificationServiceTests.cs` و`AdminNotificationServiceTests.cs` و`NotificationOutboxProcessorTests.cs`. تبقى أدوات `scripts/debug/NotificationAudit` لإعادة الإنتاج، ولا تُعد اختبارات الإنتاج البديلة الوحيدة.
- تحديد شكل الاستضافة ووجود أكثر من عامل أو نسخة IIS، وقراءة أسماء الأدوار والصلاحيات المستخدمة للإشعارات دون تعديل بيانات البيئة.

**القبول:** وجود اختبارات تفشل للأخطاء المطلوب إصلاحها، ونتيجة أساس موثقة. تعذر إعداد SQL لا يمنع كتابة الإصلاحات والاختبارات الوحدوية، لكنه يبقي قبول الأقفال والمعاملات معلقًا حتى اختبار SQL مستقل.

## NF1 — الحذف والجلسة وحدود المرفقات

### 1. الحذف الجماعي

- في `AdminNotificationService.BulkDeleteAsync`: رفض الطلب الذي لا يحدد IDs أو مرشحًا فعليًا أو `DeleteAll=true`. `OnlyRead=false` وقائمة IDs فارغة لا يعتبران اختيارًا.
- تعريف معنى اجتماع `DeleteAll` والمرشحات: التطبيق يبقى على المجموعة المحددة بالمرشحات، ولا يؤدي `Where(true)` إلى توسيعها. رفض الاختيارات المتعارضة بدل تفسيرها بصمت.
- الاحتفاظ بسياسة `System.Admin`، وإرجاع `ApiResponse` ورسالة عربية وحالة HTTP مناسبة عبر `.ToActionResult()` للمسارات المتأثرة.
- تسجيل الحذف الإداري عبر التدقيق، بمعرّفات/معايير العملية والعدد، دون تحميل محتوى رسائل المستخدمين في السجل.

**القبول:** `{}` وقائمة IDs فارغة و`OnlyRead=false` وحدها لا تحذف شيئًا؛ IDs محددة تحذف المحدد فقط؛ مرشح فعال يعمل ضمن نطاقه؛ الحذف الشامل يحتاج اختيارًا صريحًا؛ المستخدم غير المخول مرفوض.

### 2. تنظيف الجلسة

- ربط تركيب البطاقة والطابور بمعرّف المستخدم والجلسة؛ تصفير العناصر والمؤقّتات ومنع التكرار وإيقاف الصوت المؤجل عند الخروج أو تبديل المستخدم.
- إلغاء الطلبات وإهمال callbacks الخاصة بالجلسة السابقة. لا يكفي تصفير المتجر إذا بقيت حالة محلية أو طلب قيد التنفيذ.
- إزالة استعلامات الإشعارات الخاصة بالمستخدم السابق من الذاكرة المؤقتة عند انتهاء الجلسة.

**القبول:** الخروج وانتهاء الجلسة وتبديل الحساب يزيلان البطاقات والعدد فورًا؛ لا يظهر إشعار الحساب أ للحساب ب، حتى لو انتهى طلب أو وصل حدث قديم بعد التبديل.

### 3. حد ملكية المرفق

- إضافة خدمة وصول للمرفق ضمن خدمة الإشعارات أو واجهة محددة في Core، ومسار مثل `GET /api/notifications/{notificationId}/attachments/{attachmentId}/download`.
- التحقق من أن المرفق نشط ويتبع الإشعار المحدد، وأن المستخدم هو المستلم؛ وصول الإدارة يمر بسياسة صريحة `System.Admin`. التحقق من المسار والامتداد يبقى داخل تخزين الملفات.
- منع فتح `uploads/notifications/*` أو `/api/files/uploads/notifications/*` دون نفس فحص الملكية، أو إغلاق هذين المسارين لمرفقات الإشعارات والاعتماد على المسار الجديد. لا يُترك مسار قديم يتجاوز المسار الآمن.
- جميع استعلامات الملكية في الخدمة عبر IUnitOfWork؛ Controllers والميدل وير يستدعيان الخدمة دون استعلامات EF خام. أي اعتماد جديد يُسجَّل صراحةً في `NotificationsServiceCollectionExtensions` التي يستدعيها `Program.cs`.

**القبول:** المستلم يحصل على الملف؛ مستخدم آخر برابط معروف لا يحصل عليه؛ تطابق ID الإشعار والمرفق مفروض؛ المرفق المحذوف لا يُرسل؛ اختبارات HTTP تشمل المسار الجديد والمسارين القديمين.

## NF2 — السجل والعداد والتنبيه العائم

### 1. مصدر واحد لبيانات الخادم

- إضافة hook مشترك، مثل `ui/src/hooks/useNotifications.ts`، واستكمال `queryKeys.notifications` بمفاتيح تحتوي `userID` ثم الصفحة والتصنيف.
- الجرس وصفحة الإشعارات يستهلكان الاستعلامات المشتركة. يحصر Zustand في طابور التنبيه وحالة الجلسة/الاتصال؛ تُزال ملكيته الموازية للقائمة والعداد بعد نقل جميع المستهلكين.
- `totalCount` من الصفحة و`unreadCount` من الخادم، ولا يُشتقان من حجم آخر ١٠ عناصر. لا يخصم `markAsRead` محليًا من عدد سبق تحديثه بحدث SignalR.
- نقل mutations القراءة إلى `useApiMutation`، وإبطال الاستعلامات ذات الصلة بعد النجاح. حفظ قراءة الكل وتحديث كل الأسطح والتبويبات من نفس المصدر.

### 2. دورة الاتصال والمزامنة

- بدء الاتصال عندما تكتمل الجلسة ويوجد الرمز، وإزالة تأخير ٥ ثوانٍ غير الضروري. إزالة اعتماد تحميل السجل على علم `fresh_login`.
- الجلب الأولي وإعادة الاتصال وعودة التركيز تُعيد مزامنة القائمة والعدد؛ حالة الانقطاع تشغّل إعادة الجلب المقترحة عند ظهور الصفحة، مع إيقافها عند الخروج أو استعادة الاتصال.
- تمرير AbortSignal إلى طلبات Axios المستخدمة بالاستعلامات. تضمين هوية الجلسة يمنع نتائج طلبات قديمة من ملء حساب جديد.
- استخدام أحداث وصول الإشعار/تغير العدد كإشارات إبطال للاستعلامات، وتجميع دفعة الإبطالات خلال نافذة قصيرة مقترحة ٢٥٠ مللي ثانية. لا يُعامل العدد المدفوع كنسخة أحدث مطلقًا، لأنه قد يتسابق مع قراءة HTTP.
- التعامل مع فشل طلب القائمة أو العدد بشكل مستقل؛ فشل أحدهما لا يمنع الاستفادة من الآخر. تعاد المحاولة وفق حالة الاتصال دون عرض أخطاء متكررة للمستخدم.

### 3. الطابور والمؤقّت

- يضيف `ReceiveNotification` كل حدث جديد للطابور بمعرّفه؛ لا يقرأ المكوّن أول عنصر من السجل.
- حفظ وقت العرض/المتبقي فعليًا، وتحديد إزالة مرحلة الخروج مستقلًا عن العد التنازلي؛ تنظيف جميع مؤقّتات العرض عند الإغلاق والإزالة.
- استخدام حد ٣ مرئية، وإظهار المنتظر عند انتهاء بطاقة؛ إيقاف المؤقّت أثناء hover. اختبار القفزات الزمنية والانتقال للخلفية و`prefers-reduced-motion`.
- منع التكرار قبل جميع الآثار: الطابور والصوت وToast. اختيار البطاقة وحدها لأحداث الإشعارات، مع احترام كتم الصوت. محتوى إشعار موجود يمكن تحديثه دون إصدار تنبيه جديد بنفس ID.
- الحد المقترح للطابور/سجل منع التكرار يُحدَّد صراحةً ويُختبر؛ يمكن البدء بطابور ٥٠ وحد منفصل لمنع التكرار. إعادة الجلب لا تعيد إظهار السجل القديم، ولا يُفقد السجل بسبب بلوغ حد العرض.

### 4. النقر

- إضافة محلّل وجهة واحد يفضل `actionUrl` داخليًا صالحًا، ثم `RelatedTableID/relatedRecordID` عندما يكون النوع معروفًا. لا تُستنتج الوجهة المالية من وجود كلمة «تسوية» في العنوان.
- فتح البطاقة والجرس والصفحة يعمل بالوجهة نفسها، ويحدّث القراءة عبر mutation موحدة. الإغلاق وحده لا يغيّر القراءة. بطاقة قابلة للاستخدام بلوحة المفاتيح واسم واضح لزر الإغلاق.
- إضافة `relatedTableID` إلى النوع الأمامي إذا كان مطلوبًا للمحلّل؛ الخادم يرسله بالفعل. يبقى تفويض الصفحة المستهدفة مستقلًا عن ظهور الإشعار.

**القبول:** N01–N09 وN16 تتحول إلى نتائج صحيحة، مع اختبارات ٢٥ غير مقروءًا مقابل صفحة من ١٠، وحدث مكرر، و٣ أحداث مجمعة، وتحديث السجل أثناء وصول رسالة، وStrictMode، وتبديل المستخدم، وترتيبي وصول استجابة القراءة وحدث العدد. قراءة الكل تصحح الجرس والصفحة والتبويب الثاني.

## NF3 — المستلمون والمعاملات

- توثيق جدول لكل منادي: الحدث، نوع السجل، مستلموه، نطاق الفرع، والخدمة التي تملك المعاملة. يشمل الملفات والتسويات والرواتب والاستحقاقات وخدمات المستخدمين.
- استبدال `Accountant` و`Manager` بأسماء/قواعد المستلمين الفعلية بعد مقارنة Seeds والصلاحيات والبيانات الحالية؛ لا تُنشأ أدوار جديدة لتغطية خطأ تسمية، ولا تُغيّر أدوار المستخدمين تلقائيًا.
- عدم الاعتماد على أرقام `RoleConstants` قبل مطابقتها للبيانات؛ الملف الحالي يوثّق معرّفات لا تكفي لتحديد اسم المستلم أو صلاحياته.
- الإشعارات المالية تستهدف المستخدمين النشطين المخولين في نطاق فرع المعاملة، مع قواعد المستخدمين المركزيين كما تسمح سياسة النظام. البث الإداري إلى دور عالمي يبقى اختيارًا صريحًا منفصلًا.
- اختيار صفر مستلمين: الإرسال الإداري المباشر يعيد نتيجة عربية توضح عدم وجود مستلمين؛ إشعار أعمال بلا مستلم لا يحول عملية مالية سليمة إلى فشل، لكنه يُسجَّل كحالة قابلة للمتابعة. لا يُرسَل بدلًا منه لكل المستخدمين.
- استبدال إشعار ما بعد `Commit` في إنشاء الملف والمنادين المشابهين بـ`EnqueueAsync`/`EnqueueRoleAsync` داخل معاملة المالك، مع الحفظ النهائي قبل Commit. إذا احتاج الملف Identity، يحصل عليه بـSaveChanges داخل المعاملة ثم تُجهّز الرسالة.
- الحفاظ على ISoDGuard والتدقيق ونطاق الفرع؛ أي تعديل constructor يُرافقه تحديث mocks في نفس الدفعة.

**القبول:** الحدث يصل للمستلمين المخولين فقط؛ معاملات فرع أ لا ترسل لفرع ب دون قاعدة صريحة؛ مستخدم غير نشط مستبعد؛ rollback للعمل لا يترك إشعارًا أو Outbox؛ نجاح Commit يثبت الثلاثة معًا. تحقق المعاملة الأخيرة باختبار SQL، لا باختبار Moq فقط.

## NF4 — متانة عامل الإرسال

- فصل نجاح بث الرسالة عن إخفاق بث العدد: إخفاق `UnreadCountUpdated` وحده لا يضع الرسالة الناجحة في دورة إعادة إرسال. يُسجل الإخفاق وتتعافى الواجهة بالمزامنة.
- تعديل التعليق الخاطئ في `PushUnreadCountAsync` وإضافة سجل إخفاق محدود. تُختبر النتيجة عند انقطاع الاتصال وعند وجود معاملة نشطة.
- إضافة حجز ذري لدفعة Outbox بمدة ملكية ومعرّف حجز. تصميم مقترح: `LockedUntilUtc` و`ProcessingToken` دون إعادة ترقيم `OutboxStatus`. التحديث/الإكمال يشترطان امتلاك الحجز، والحجز المنتهي يمكن استعادته بعد توقف العامل.
- واجهة المستودع المتخصص في `PensionMS.Core/Interfaces/Notifications/`، وتنفيذ SQL في Infrastructure، وتسجيل صريح في DI. تُستخدم صيغة UPDATE/OUTPUT مع أقفال مناسبة وتُختبر على SQL Server؛ لا يُعامل الاستعلام ثم تعديل الكيانات لاحقًا كحجز.
- حقول الحجز وفهارس الاستعلام تُضاف بإعدادات EF وسكربتات `scripts/notification-outbox-precheck.sql` و`notification-outbox-apply.sql` و`notification-outbox-rollback.sql`. السكربت قابل لإعادة التشغيل ولا يمسح صفوف Outbox القديمة.
- معالجة دفعات متتالية عند وجود تراكم، مع حد عمل للدورة واستجابة للإلغاء؛ الانتظار عند الفراغ/انتهاء الميزانية. قيم الدفعة والانتظار وإعادة المحاولة تكون إعدادات واضحة بحدود، لا خفضًا عشوائيًا للمؤقّت.
- تأخير إعادة المحاولة عند إخفاقات البث بدل حلقة سريعة، وحد نهائي للفشل، وإعادة محاولة إدارية مضبوطة. قص رسالة الخطأ إلى سعة العمود وإزالة المعلومات الحساسة.
- قياس أقدم عنصر معلّق، وعدد المعلّق والفاشل، وزمن معالجة الدفعات ومعدل إعادة المحاولة. لا تُسجَّل JWT أو نصوص الرسائل.

**القبول:** عاملان لا يحصلان على الحجز نفسه؛ توقف العامل يسمح باستعادة الحجز؛ عامل انتهت ملكيته لا يكمل حجزًا جديدًا؛ إعادة محاولة فشل العدد وحده لا تعيد الرسالة؛ فشل الحفظ بعد البث لا يسبب تنبيهًا مكررًا في الواجهة؛ معالجة ٥٠٠ إشعار لا تنتظر ٣٠ ثانية بعد كل دفعة عند وجود تراكم. قياس السعة ونتائج الأقفال تُوثّق على SQL مستقل.

يبقى N10 مقبولًا كتفسير للبث، مع تغيير العبارة المعروضة وعدم تسميتها «تم الاستلام». معيار إغلاق مشكلة المستخدم غير المتصل هو أن تظهر رسائله وعدده الصحيح من السجل عند عودته، لا إبقاء Outbox معلّقًا بلا نهاية.

## NF5 — المرفقات والتواريخ واستكمال تجربة الاستخدام

- ربط مسار تنزيل NF1 في `ui/src/api/notifications.ts` بمصادقة Axios و`responseType: 'blob'`. إنشاء رابط Blob مؤقت وإلغاؤه بعد الاستخدام، ومعالجة الخطأ بالعربية. لا يُوضع رمز الدخول في URL ولا تُفتح المسارات الخام مباشرة.
- توحيد سياسة رفع الإشعارات بين النموذج والخدمة والتخزين. البداية تحافظ على PDF/JPG/JPEG/PNG وحد ١٠ ميجابايت لكل ملف؛ Word/Excel تحتاج دعمًا وتحقق محتوى صريحين، فلا تعرضها النافذة كخيارات مدعومة قبل ذلك.
- عند فشل إرسال بمرفقات بعد حفظ ملفات على القرص، تنظيف الملفات التي أنشأتها هذه العملية فقط، دون لمس مرفقات قديمة أو عملية أخرى.
- استخدام UTC صريح في طوابع `CreatedAt/ReadAt/UploadedAt` في HTTP وSignalR. تحويل `DateTimeKind.Unspecified` القادم من SQL على حد التسلسل دون تغيير مخزن الوقت أو إعادة تفسير وقت محلي على أنه UTC.
- قراءة ADR 0001 والاختبارات الحالية قبل التعديل، وتحديث الوثيقة لتعكس محوّل UTC الموجود؛ التغيير المحدود يخص طوابع الإشعارات، ولا يغيّر عقود حقول التقويم الأخرى.
- استخدام `YemenTime.TodayStartUtc` وحد بداية اليوم التالي لإحصاء «اليوم»، وفترة `[from, to)` واضحة للمرشحات؛ مقارنة الوقت في الواجهة تستخدم أدوات التاريخ المركزية دون لصق Z على نص يحوي إزاحة أصلًا.
- ربط لون/أيقونة التنبيه بالنوع والتصنيف، باستخدام tokens الموجودة. توحيد النسختين الفاتحة والداكنة ودعم الحركة المخفضة والشاشات الضيقة والطباعة إذا ظهرت البطاقة فيها.

**القبول:** فتح المرفق يعمل مع فصل أصول UI/API؛ الملكية مفروضة على كل المسارات؛ النوع غير المدعوم مرفوض قبل الإرسال وبالخادم؛ المرفق المحذوف غير متاح؛ UTC غير محدد Kind يخرج UTC صريحًا؛ الساعة ٠٠:٣٠ في اليمن تدخل في إحصاء اليوم المحلي؛ الإزاحة الصريحة لا تتضاعف.

## NF6 — التحقق وتجهيز الإصدار

### بوابات كل دفعة

- Frontend من `ui/`: حفظ lint قبل وبعد → `npm.cmd run lint` → `npm.cmd run build` → `npm.cmd test` → `npm.cmd run preview` للتحقق البصري. معيار lint عدم إضافة مشكلات إلى الأساس المحفوظ، لا افتراض عدد قديم أو اشتراط صفر.
- Backend: `dotnet build --nologo` من `PensionMS.API/` و`dotnet test --nologo` من `PensionMS.Tests/`. Controllers ومسارات HTTP تُختبر في `PensionMS.IntegrationTests` التي تشير إلى API، لا يُفترض أن الاختبارات الوحدوية الأصلية تغطي Program أو المصادقة.
- SQL: قاعدة اختبار مستقلة باسم اختبار، عبر إعداد `PENSIONMS_TEST_SQLSERVER`؛ اختبارات المعاملة والحجز والفهارس دون حذف/تعديل قاعدة الأعمال.
- تشغيل حالة المتصفح الأصلية وتحديث مقارناتها، وإضافة الاختبارات الجديدة. اختبارات أدوات التشخيص تُحدَّث عندما يتغير العقد؛ لا تُترك assertions تثبت الحذف الشامل أو العدد الخاطئ ثم تُعد نجاحًا للإصلاح.

### سيناريوهات القبول النهائية

| السيناريو | النتيجة المطلوبة |
|---|---|
| إنشاء ملف | بيانات الملف وNotification وOutbox تثبت معًا، والوجهة تفتح الملف الصحيح. |
| الدخول/إعادة تحميل الصفحة | الجرس والعدد صحيحان؛ السجل القديم لا يفتح بطاقات. |
| انقطاع ثم عودة الاتصال | استعادة السجل والعدد دون تكرار البطاقات أو الصوت. |
| بقاء الانقطاع | إعادة جلب محدودة عندما تكون الصفحة مرئية؛ تتوقف عند الخروج. |
| ٢٥ غير مقروءًا مع صفحة من ١٠ | العدد يظل ٢٥، وحجم الصفحة مستقل. |
| قراءة إشعار من تبويبين | لا خصم مزدوج؛ كل الأسطح تستعيد نفس الحالة. |
| حدث مكرر ودفعة أحداث | تنبيه واحد لكل ID، وعدم فقد الأحداث المجمعة من الطابور. |
| انتهاء ٧ ثوانٍ وhover | شريط متناقص وإيقاف مؤقت صحيح وإزالة كاملة للبطاقة. |
| خروج وتبديل حساب أثناء الطلب | لا بطاقة أو صوت أو استجابة تخص الحساب السابق. |
| إرسال مالي بحسب الدور/الفرع | المستلمون مخولون ونشطون ضمن النطاق المحدد. |
| عاملان وتوقف أحدهما | حجز صحيح واستعادة بعد التوقف وإكمال من المالك فقط. |
| طلب حذف فارغ | رفض وصفر حذف مع سجل تدقيق للإجراء الإداري الصحيح. |
| مرفق برابط معروف لمستخدم آخر | رفض عبر المسار الجديد والقديم، وتنزيل سليم للمستلم. |
| حدود منتصف ليل اليمن | الإحصاء والوقت متسقان بين HTTP وSignalR والواجهة. |

### ترتيب النشر والتراجع

1. حفظ أدلة الاختبار ومراجعة الفرق والمخطط في بيئة تجربة.
2. تطبيق الحقول الإضافية والفهارس بعد precheck ومراجعة قاعدة الهدف. الحقول تكون متوافقة مع السجلات الحالية.
3. عند اعتماد الحجز، إيقاف/تصريف العامل القديم أثناء الانتقال؛ العامل القديم لا يحترم حقول الحجز الجديدة، فلا يُفترض أن تشغيل النسختين معًا آمن.
4. نشر API ثم UI بوسائل المشروع `deploy-api.ps1` و`deploy-ui.ps1`، وإعادة تشغيل عامل واحد ثم زيادة النسخ بعد التحقق من الحجز. النشر وتطبيق قاعدة الهدف مرحلتان لاحقتان، وليستا جزءًا من إعداد هذه الخطة.
5. مراقبة زمن التراكم والفشل وعدد البث وتطابق العدّاد بعد الإصدار.
6. التراجع يحافظ على Notification وOutbox وبيانات الأعمال. تُترك الحقول الإضافية عند الرجوع إلى إصدار أقدم إلى أن تُتأكد خلوّ تبعياتها؛ rollback المخطط لا يُنفَّذ فوق عامل يستخدم الحقول. تُحافظ إصلاحات حماية الحذف والملكية على استقلالها لتجنب فقدها عند التراجع عن تحسينات المعالج.
