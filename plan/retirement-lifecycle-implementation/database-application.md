# تطبيق حالات ملفات التقاعد على قاعدة البيانات

## نطاق التطبيق

السكربت التنفيذي: [retirement-lifecycle-rollout.sql](../../scripts/retirement-lifecycle-rollout.sql).

هذا تحويل لبيانات السجلات الموجودة، دون إضافة أو تعديل تعريف كيان أو جدول أو عمود. إلغاء فصل المهام تغيير في التطبيق فقط، ولا يتطلب تحديثًا لقاعدة البيانات أو تعديل صلاحيات المستخدمين.

## خطوات التنفيذ

1. إكمال التحقق من إصدار التطبيق وتجربته مع نسخة مستعادة من القاعدة المستهدفة.
2. أخذ نسخة احتياطية قابلة للاستعادة، وإيقاف كتابة المستخدمين والمهام الخلفية أثناء نافذة التحويل.
3. نشر إصدار API والواجهة المتوافقين قبل إعادة فتح الاستخدام.
4. فتح السكربت في SQL Server Management Studio، واختيار قاعدة PensionMS المستهدفة من قائمة قواعد البيانات. يمكن التحقق منها بتشغيل `SELECT DB_NAME() AS TargetDatabase;`.
5. تشغيل السكربت كما هو، بقيمة `@Apply = 0`. هذا يعرض أعداد السجلات المراد تحويلها حسب الحالة الحالية وعدد السجلات المحذوفة المحفوظة، دون إجراء التحويل.
6. تحديد مستخدم مسؤول فعّال لتوثيق العملية. للاستعلام عن المستخدمين: `SELECT UserID, Username, FullName FROM dbo.Users WHERE IsActive = 1;`.
7. في نسخـة التنفيذ من السكربت، تغيير `DECLARE @Apply bit = 0;` إلى `DECLARE @Apply bit = 1;`، وتغيير `DECLARE @ActorUserID int = NULL;` إلى رقم المستخدم المختار، ثم تشغيل السكربت كاملًا.
8. التحقق من العدد الناتج في `QueuedForReview`، ثم فحص قائمة المراجعة وتفاصيل الملفات وحالة المعاش من التطبيق، وإعادة فتح الاستخدام بعد نجاح التحقق.

## الأثر المتوقع

- جميع سجلات ملفات التقاعد غير المحذوفة وقت التحويل تصبح `StatusID = 6` و`ReviewStatus = 1`: معلق / بانتظار المراجعة، بما فيها الملفات التي كانت جديدة أو نشطة أو بحالات قديمة.
- يضاف إيقاف صرف للمراجعة لكل ملف إذا لم يكن موجودًا. إيقافات المعاش المستقلة تبقى نافذة. الإيقاف القديم المرتبط بالحالة 3 يُحفظ كإيقاف مستقل إذا لم يكن له إيقاف مستقل قائم.
- تُحفظ البيانات والمدفوعات والتاريخ، وتُنشأ نسخة أساس لحساب المبالغ أثناء المراجعة عندما لا توجد نسخة محفوظة مناسبة. لا يُرسل السكربت أموالًا ولا يسجل المبالغ الموقوفة كبنود مستلمة.
- الملفات التي انتهى استحقاقها تحفظ هذا القصد في `PreviousStatusID = 4`؛ اعتماد تصحيح بياناتها لا يعيد استحقاقها تلقائيًا. إعادة الاستحقاق إجراء صريح على الملف نفسه ثم مراجعة واعتماد.
- السجلات المحذوفة منطقيًا تبقى محذوفة ومحفوظة. جداول الحالات القديمة تبقى مرجعًا للتاريخ؛ لا تُحذف منها القيم التي قد تشير إليها سجلات قديمة.
- العملية تستخدم معاملة واحدة، ويسجل كل ملف في التدقيق. إعادة تشغيل نفس إصدار التحويل لا تعيد تعليق الملفات التي سبق تحويلها به، حتى إن اعتُمدت لاحقًا. لذلك لا يُغيّر `@RolloutID` عند إعادة المحاولة.

## فحص ما بعد التنفيذ

```sql
SELECT StatusID, ReviewStatus, COUNT_BIG(*) AS FilesCount
FROM dbo.RetirementFiles
WHERE IsDeleted = 0
GROUP BY StatusID, ReviewStatus;

SELECT COUNT_BIG(*) AS FilesWithoutReviewHold
FROM dbo.RetirementFiles f
WHERE f.IsDeleted = 0 AND f.StatusID = 6 AND f.ReviewStatus = 1
  AND NOT EXISTS (
    SELECT 1 FROM dbo.PensionSuspensions s
    WHERE s.FileID = f.FileID AND s.IsDeleted = 0
      AND s.SuspensionSource = N'مراجعة بيانات الملف'
      AND s.Status IN (N'فعّال', N'Active')
  );
```

مباشرة بعد التحويل وقبل قرارات المراجعة، يفترض أن تكون الملفات الحالية في المجموعة `(6, 1)`، وأن يكون `FilesWithoutReviewHold = 0`.

لم يُشغّل التحويل على قاعدة النظام الفعلية ضمن إعداد هذا التغيير. لا يوجد إجراء رجوع آلي يمحو قرارات المراجعة اللاحقة؛ خطة الرجوع أثناء نافذة التحويل تعتمد على النسخة الاحتياطية وإصدار التطبيق المتوافق معها.
