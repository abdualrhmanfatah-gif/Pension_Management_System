# رسالة إرسال المراجعة مع بقاء الحالة القديمة — 2026-10-21

## ما ثبت بالاختبار

1. `RetirementFilesController.GetById` كان يحتفظ باستجابة تفاصيل الملف في `IMemoryCache` لمدة خمس دقائق. كانت مسارات التحديث وتسجيل الوفاة وتصحيحها تمسح هذا الإدخال، بينما مسارات إرسال المراجعة وإعادة الاستحقاق واعتمادها ورفضها والتعديلات من الخدمات المرتبطة لا تمسحه.
2. اختبار `RetirementFileReviewRefreshTests.Read_Submit_Read_ReturnsPersistedReviewStateImmediately` يقرأ ملفًا جديدًا، ثم يستدعي الإرسال الصريح ويثبت تغير الحالة في مصدر القراءة، ثم يعيد القراءة. قبل الإصلاح فشل: المتوقع `6` والفعلي `1`. سجل التنفيذ: `review-refresh-before.txt`.
3. اختبار المتصفح على السياق المعزول يمر عبر الزر الحقيقي وعميل API الحقيقي و`useApiMutation`؛ عند إعادة نجاح HTTP مع بقاء الملف جديدًا، ظهرت رسالة النجاح الثابتة رغم عدم تغير الحالة. لم تُستخدم بيانات مستخدم أو قاعدة حقيقية في هذا الاختبار. النتيجة محفوظة في `review-submit-browser-before.json`.

## الإصلاح

- إزالة تخزين تفاصيل الملف المؤقت من المتحكم، بما فيه مدد التخزين وإبطال الإدخالات الذي أصبح غير مستخدم. القراءة تمر مجددًا بالخدمة ونطاق الفرع في كل طلب، ولذلك تغطي تغييرات الملف من أي كيان مرتبط.
- إضافة `submitAndConfirmFileReview`: يفحص نجاح الاستجابة وبياناتها، ثم يقرأ الملف ويتحقق من `StatusID = 6` و`ReviewStatus = 1` قبل السماح برسالة النجاح.
- استخدام رسالة الخادم بعد تأكيد الحالة بدل الرسالة الثابتة. فشل القراءة أو بقاء الحالة القديمة أو رفض العملية يعرض خطأ، ولا يدعي نجاح الإرسال.
- اختبارات الواجهة تغطي نجاح الطلب مع بقاء الجديد، وفشل العملية، وبقاء المراجعة مرفوضة، والتأكيد الناجح، وفشل قراءة التأكيد.

## حدود الاستنتاج

هذه الأسباب مثبتة في الكود ومسارات الاختبار. لا تتضمن هذه النتائج تحققًا من سجل الملف المحدد الذي أبلغ عنه المستخدم، لأن رقم الملف لم يكن متاحًا عند التشخيص. يلزم نشر/تشغيل إصدار API المصحح والواجهة المصححة حتى يسري الإصلاح في التطبيق الجاري؛ البناء المعزول لا يستبدل عملية API الحالية.
